# MY XR UNIVERSE 강사 운영 가이드

## 목표와 대상
고등학생 XR 전공 기초 수준을 가정한 50분 × 3교시 수업입니다. 수업 중 최종 결과는 XR 아이디어 소개 웹 포트폴리오이며 실제 VR/AR 앱 구현과 구분합니다. 11명이 자기 기록과 협업 기록을 남깁니다.

## 수업 전 확인
1. GitHub 로그인과 이메일 인증을 미리 확인합니다. 학교·보호자 정책에 따라 계정을 준비합니다.
2. AI 도구 사용 가능 여부, 텍스트 편집기, HTML 다운로드와 실행을 확인합니다.
3. 활동 번호 01–11을 배정하고 짝 4팀과 3인팀 1팀을 구성합니다.
4. 학생에게 수업 홈을 배포하고 제출할 LMS/폼/폴더를 별도로 안내합니다. 워크북에는 서버 전송 기능이 없습니다.
5. GitHub Pages 설정을 강사 계정에서 한 번 리허설합니다. 학생 개별 계정에 대신 로그인하지 않습니다.

## 협업 리허설
학생 개인 홈페이지 저장소는 my-xr-universe, 강사 저장소를 Fork할 이름은 xr-class-collab입니다. Fork 안에서 idea-활동번호 브랜치를 만들고 collaboration/ideas/student-활동번호.md 하나만 고칩니다. PR의 base는 chloeisLovely/my-xr-universe:main입니다. 학생 계정을 collaborators로 초대하지 않아도 공개 저장소의 Fork 방식으로 제안할 수 있습니다. 계정 정책에 따라 Fork/PR이 제한될 수 있으므로 사전 확인합니다.

강사는 Files changed에서 파일 범위와 내용을 읽고 피드백합니다. 개인정보·완료 과장·불필요한 파일 변경이 없으면 Merge합니다. 학생 PR은 Refs #1을 사용하며 Closes #1을 쓰지 않습니다. 학생 PR을 모두 수업 중 병합할 필요는 없습니다.

- AI 사용 불가: collaboration/README.md의 강사 예시를 검토하고 자기 내용으로 수정합니다.
- 로그인 지연: 짝 활동 + README/HTML 로컬 작성 후 후속 업로드.
- 배포 지연: 로컬 실행과 친구 검토를 먼저 진행하고 공개 URL은 배포 성공 뒤 확인.
- 파일 다운로드 제한: ZIP의 templates/cosmos, studio, arcade/index.html 중 하나 제공.
- 변경 안 됨: 저장 여부, MY_PROFILE 중복, 따옴표·쉼표, 올바른 파일, 강력 새로고침 순서.
- 404: 웹 주소, main의 최상위 index.html, Pages main/(root), Actions 상태 확인.
- Fork 이름 충돌: xr-class-collab으로 바꾸거나 기존 Fork 재사용.
- PR 비교 없음: 작업 branch에 실제 Commit했는지, base/head 선택 확인.
- 워크북 저장 제한: JSON 백업 사용. 브라우저 데이터 삭제나 공용 PC 초기화 전 백업 확인.

## 슬라이드별 강의 스크립트

### 01. MY XR UNIVERSE

[진행 1교시 0–2분] 오늘 여러분은 자신의 관심과 아이디어를 다른 사람에게 보여 줄 주소를 만들 겁니다. 이미 개발을 잘해야 시작할 수 있는 것은 아니에요. 오늘 어디까지 만들었는지 솔직하게 기록하는 것도 개발의 중요한 부분입니다.
[질문] 내가 좋아하는 게임이나 전시를 직접 바꿀 수 있다면 무엇을 바꾸고 싶나요? 두 학생의 답을 듣습니다.
[시각 자료] 표지는 AI 생성 개념 이미지입니다. 실제 XR 기기 제품이나 실제 학생 활동 사진이 아닙니다.

### 02. 오늘 남길 세 가지 결과

[진행 2–5분] 오늘의 완료 기준을 먼저 보여 줍니다. 홈페이지가 멋진 것도 좋지만, 내가 무엇을 바꿨는지 설명하는 것이 더 중요합니다. 마지막에는 친구 기기에서 내 주소를 열어볼 거예요.
[강사] 학생마다 GitHub 로그인 여부를 손들기로 확인합니다. 가입·인증 문제가 있는 학생은 짝과 함께 관찰하고 로컬 기록을 남기게 합니다.
[유의] 50분 수업 3회이며 쉬는 시간은 별도입니다. 처음부터 XR 실행 앱을 만드는 수업으로 오해하지 않도록 소개 페이지가 최종 결과라고 설명합니다.

### 03. 기술을 보는 눈

[진행 5–8분] 공중에 뜨는 건물 같은 답도 좋고, 길을 찾기 쉬운 안내도 좋습니다. 답을 평가하지 않고 대상과 이유를 묻습니다. “그 기능을 누가 가장 좋아할까요?”
[참여] 짝에게 20초씩 말하게 하고 두 가지 답을 전체에 공유합니다. 11명은 2명씩 4팀과 3명 1팀으로 운영할 수 있습니다.
[연결] 기술 이름보다 먼저 사람의 경험을 떠올렸다는 점을 짚고 다음 슬라이드로 이동합니다.

### 04. VR, AR, 3D의 차이

[진행 8–12분] VR은 가상 전시관 안에서 작품을 보는 경험, AR은 카메라로 책상을 비추면 그 위에 안내가 겹치는 경험으로 설명합니다. 3D 모델은 입체 자료이며 모든 3D 화면이 XR은 아닙니다.
[질문] 휴대폰으로 방을 비추고 가상 가구를 놓는 것은 어느 쪽에 가까울까요? AR이라는 답과 함께 실제 공간 위에 정보를 더한다는 근거를 말하게 합니다.
[범위] 오늘 HTML 포트폴리오에는 아이디어를 소개합니다. 헤드셋 연결이나 실제 AR 추적 기능은 구현하지 않습니다.

### 05. AI와 사람이 맡는 일

[진행 12–15분] AI에게 “멋진 걸 만들어 줘”라고 하면 무엇이 좋은지 판단 기준이 없습니다. 내가 누구를 위해 무엇을 만들지 결정하면 AI가 도울 범위가 분명해집니다.
[시연] 전시관이라는 아이디어에 대상과 불편을 추가해 말해 봅니다. AI 결과를 실제로 실행하지 않았다면 “실행 확인 필요”로 남깁니다.
[유의] 특정 AI 제품의 무료 사용량이나 최신 기능은 단정하지 않습니다. 학교에서 허용한 도구를 사용하며 AI 이용이 막히면 준비한 예시 초안으로 검토 활동을 진행합니다.

### 06. GitHub의 네 가지 역할

[진행 15–19분] 게임의 저장 슬롯을 떠올려 보세요. GitHub에서는 파일과 함께 무엇을 바꿨는지도 남길 수 있습니다. 친구가 제안한 변경을 살펴보고 합치는 과정도 있습니다.
[질문] 파일 이름을 최종, 진짜최종, 진짜최종2로 바꿔본 적 있나요? 짧게 손을 들어봅니다. Commit은 변경 내용을 기록한 지점을 만드는 것으로 설명합니다.
[출처] https://docs.github.com/en/get-started/using-github/hello-world

### 07. 저장소와 README

[진행 19–22분] 저장소는 프로젝트 단위의 공간입니다. README는 무엇을 만들고 있는지 알려 주는 첫 안내문입니다. 아직 완성하지 않았어도 관심과 계획을 적을 수 있어요.
[시연] 강사 저장소의 파일 목록과 README를 보여 줍니다. 코드 화면과 실제 웹페이지가 다르다는 점을 짚습니다.
[출처] https://docs.github.com/en/get-started/using-github/hello-world

### 08. 기억에 남는 Commit 메시지

[진행 22–25분] 같은 파일을 여러 번 고쳤을 때 제목만으로 변경 내용을 찾을 수 있으면 편합니다. “수정”이라는 메시지가 틀린 것은 아니지만 정보를 주기 어렵죠.
[참여] “이름 바꿈”, “소개 글 추가”를 더 구체적인 Commit 메시지로 바꿔보게 합니다. 예: “닉네임을 NOVA로 변경”.
[출처] https://docs.github.com/en/get-started/using-github/hello-world

### 09. MISSION 01 · 내 저장소

[실습 25–33분] 강사가 한 단계 실행한 뒤 학생이 따라오도록 멈춥니다. Owner가 학생 본인인지 확인합니다. 기존 같은 이름의 저장소가 있으면 새로 만들지 않고 그 저장소를 사용합니다.
[확인 질문] 지금 주소의 github.com 바로 다음 부분이 내 사용자명인가요?
[문제 대응] 이메일 인증·계정 이용 문제가 있으면 해결에 수업 전체를 쓰지 않습니다. 짝과 공동 관찰하고 로컬 README 초안을 작성한 뒤 후속 확인 항목으로 남깁니다.
[출처] https://docs.github.com/en/get-started/using-github/hello-world

### 10. README에 담을 내용

[실습 33–42분] README의 연필 버튼을 눌러 편집합니다. 프롬프트 P02를 쓸 수 있지만 자신의 생각과 다른 표현은 고칩니다. 기술을 배워보고 싶은 것과 이미 능숙한 것은 구분해 씁니다.
[시연] 제목 앞의 #은 Markdown 제목 표시입니다. 학생은 여기서 문법 전체를 외울 필요가 없습니다.
[검증] Preview로 읽어 보고 Commit changes를 눌러 “README에 XR 관심 분야 추가”로 저장합니다. 실명·연락처·개인 사진이 필요하지 않습니다. 예시는 실제 학생의 정보가 아닙니다.

### 11. 워크북에 남기는 첫 기록

[실습 42–45분] 웹워크북의 MISSION 01에 기록합니다. 같은 브라우저에서는 새로고침해도 유지되지만 다른 기기로 자동 동기화되지 않습니다.
[시연] JSON 백업을 눌러 파일 저장 위치를 확인합니다. 수업 제출은 별도로 강사가 안내한 경로를 이용합니다. 이 웹사이트에는 강사에게 자동 전송하는 기능이 없습니다.
[주의] 공용 PC에서는 수업 끝에 백업 후 초기화합니다. 화면의 NOVA는 설명용 예시입니다.

### 12. 1교시 체크아웃

[정리 45–50분] 옆 친구가 README를 읽고 관심 분야를 알아맞히게 합니다. 잘 보이지 않으면 소개를 한 문장 더 구체적으로 고칩니다.
[이해 확인] README는 무엇을 하는 파일인가요? Commit 메시지에는 무엇을 쓰면 좋을까요? 저장소를 만드는 것만으로 예쁜 홈페이지가 바로 생기는 걸까요? 마지막 답은 아직 HTML 업로드와 Pages 설정이 필요하다는 것입니다.
[강사 확인] 저장소 주소가 없는 학생만 표시하고 쉬는 시간에 지원합니다. 학생 계정이나 민감한 내용을 공개 명단에 모으지 않습니다.

### 13. AI와 함께 아이디어 다듬기

[진행 2교시 0–5분] 첫 시간에 내 관심을 기록했습니다. 이제 혼자 만든 문장을 다른 시각으로 읽어볼 겁니다. AI의 제안도 친구의 의견도 내가 판단할 재료입니다.
[복습] 저장소, README, Commit 중 “변경 내용을 남기는 기록”에 해당하는 말을 고르게 합니다. 정답 Commit.
[시각 자료] 협업 장면은 AI 생성 개념 이미지이며 실제 학생 사진이 아닙니다.

### 14. 질문에 넣을 네 가지

[진행 5–8분] “XR 프로젝트 추천해 줘”도 시작은 될 수 있습니다. 하지만 대상과 불편을 더하면 답을 비교할 기준이 생깁니다.
[예시] 신입생이 다른 학과 작품을 잘 모른다는 문제를 줍니다. “초보자가 첫 실험을 할 수 있도록 핵심 기능 하나와 성공 기준을 표로 써 줘”라고 범위와 결과 형식을 붙입니다.
[활동] 워크북의 대상과 불편을 먼저 두 줄로 작성하게 합니다. 아직 모르겠으면 예시를 그대로 쓰기보다 관심 대상부터 골라보게 합니다.

### 15. 같은 아이디어, 구체적인 요청

[실습 8–15분] 프롬프트 P03을 열어 자신의 아이디어를 넣습니다. AI에게 요청하기 전에 마지막 문장을 소리 내어 읽습니다. 내가 무엇을 받아야 하는지 이해되는지 확인합니다.
[강사] 두 답변을 실시간으로 받을 수 있으면 범위 차이를 비교합니다. 서비스 이용이 어려우면 아래 예시로 진행합니다: 사용자 행동=작품 선택, 화면 반응=설명 표시, 첫 실험=종이 화면으로 작품 찾기, 성공 기준=친구가 설명 없이 목표 작품 찾기.
[완료] 워크북에 대상·불편·경험을 적습니다.

### 16. AI 답변의 확인 표시

[진행 15–18분] AI 답변에 “무료로 모든 기기에서 됩니다”라는 말이 있으면 어떤 근거가 필요할까요? 공식 문서의 기능, 요금 조건, 브라우저 지원을 확인해야 합니다.
[활동] P04로 자신의 답변을 검토하고 고칠 표현 하나를 선택합니다. 무조건 틀렸다고 결론 내리는 대신 확인할 근거를 찾습니다.
[예상 질문] AI가 출처 링크를 주면 믿어도 되나요? 링크를 열어 실제로 그 주장을 뒷받침하는지 확인해야 한다고 답합니다.

### 18. Issue와 Pull Request

[진행 20–23분] 학급 공동 미션 Issue #1을 엽니다. 여기에는 해야 할 일과 완료 기준이 있습니다. PR에는 내가 실제로 바꾼 파일이 들어갑니다.
[비유] Issue는 전시에 필요한 작품 제안 안내문, PR은 내 작품을 전시에 넣어 달라는 제출 요청이라고 설명합니다. Merge는 강사가 검토 후 반영하는 단계입니다.

### 19. 개인 저장소와 공동 실습

[실습 23–27분] 강사 저장소에서 Fork를 누릅니다. 이름을 xr-class-collab으로 바꿉니다. 첫 시간에 만든 개인 저장소와 같은 이름을 사용하면 충돌할 수 있습니다.
[설명] Fork는 다른 소유자의 저장소를 내 계정으로 복사해 작업하는 방식입니다. Branch는 한 저장소 안에서 변경 흐름을 나누는 것입니다. 둘은 같은 말이 아닙니다.
[확인] 화면 주소의 소유자는 내 계정, 저장소 이름은 xr-class-collab인지 확인합니다. 이미 해당 Fork가 있으면 재사용합니다.

### 21. Commit 후 PR 만들기

[실습 32–38분] Commit 메시지는 “01번 가상 전시관 아이디어 추가”처럼 씁니다. Contribute의 Open pull request 또는 Compare & pull request를 이용합니다.
[필수 점검] base repository가 chloeisLovely/my-xr-universe, base branch가 main인지 확인합니다. head repository는 내계정/xr-class-collab, compare branch는 내 번호 브랜치입니다. Files changed에서 자기 파일 하나가 바뀌는지 확인한 뒤 생성합니다.
[오류 대응] There isn’t anything to compare가 보이면 브랜치 선택과 Commit 완료 여부를 확인합니다.

### 22. 검토할 수 있는 PR 설명

[실습 38–41분] P06을 참고하되 실제로 수행한 내용만 씁니다. 공동 Issue #1을 참조할 때 Refs #1을 사용합니다. Closes #1을 쓰면 Merge 시 학급 전체 이슈가 종료될 수 있으므로 사용하지 않습니다.
[시연] PR 양식의 체크박스를 실제 확인한 것만 표시합니다. AI가 “모든 테스트 통과”라고 쓰면 직접 확인하지 않은 문장을 삭제합니다.
[완료] 생성된 PR 주소를 워크북에 기록합니다. 한 학생이 막히면 짝의 PR을 함께 읽고 본인 초안은 로컬에 보관합니다.

### 23. 친구에게 도움이 되는 피드백

[실습 41–45분] 옆 친구 PR을 읽고 좋은 점 하나와 질문 하나를 남깁니다. AI P07은 초안 도구이며 최종 문장은 학생이 직접 읽고 고칩니다.
[시연] 강사는 학생 PR 하나의 Files changed를 보여 주고 검토 기준을 말합니다. 본문을 읽지 않고 승인하거나 Merge하지 않습니다.
[권한] Merge는 강사만 진행합니다. 모든 학생 PR을 수업 중 동시에 병합하려고 하지 않아도 됩니다. PR 생성과 피드백까지를 학생 완료 기준으로 삼습니다.

[예시] “저는 신입생을 위한 작품 전시관을 생각했습니다. 오늘은 Cosmos 디자인에서 소개와 프로젝트를 바꿨습니다. 다음에는 종이 화면으로 친구가 작품을 찾는지 확인해 보겠습니다.”
[관점] 디자인의 화려함보다 대상·수정 내용·다음 행동을 구체적으로 설명한 점을 피드백합니다.

### 38. 오늘의 기록, 다음 Commit

[정리 47–50분] 최종 제출 항목을 확인합니다. 강사가 사전에 정한 학교 LMS 또는 폼으로 제출합니다. 웹워크북 자체는 전송 기능이 없으며 JSON 또는 PDF로 저장해 제출합니다.
[확인] 공개 URL이 아직 준비되지 않았으면 “배포 대기”로 표시하고 나중에 확인합니다. 공용 PC에서는 백업 확인 후 워크북을 초기화하고 개인 계정에서 로그아웃합니다.
[마무리 멘트] 오늘 만든 페이지는 지금의 관심과 첫 시도를 담고 있습니다. 다음에 바꿀 작은 한 가지가 정해졌다면 다음 Commit을 시작할 준비가 된 것입니다.

### 39. 강사 준비와 운영

[강사용 부록] 전날 개인 학습용 계정 로그인과 이메일 인증, 학교 네트워크에서 GitHub와 AI 접근, HTML 다운로드·편집·브라우저 실행을 확인합니다. 학생 계정에 강사가 로그인하지 않습니다.
[운영] 11명은 2명씩 4팀과 3명 1팀으로 짝 검토합니다. 3인팀은 작성자·사용자·검토자로 역할을 나눕니다. 번호는 활동 식별용이며 실명과 연결된 명단을 공개하지 않습니다.
[PR] 파일 범위, 개인정보, 현재 상태, 첫 실험의 구체성을 검토한 뒤 병합합니다. 공동 Issue는 전체 활동 종료 후 닫습니다.

### 40. 진도가 달라도 남길 결과

[강사용 부록] 기본 참여 기준은 자기 생각을 기록하고 변경 내용을 설명하는 것입니다. 서비스 장애로 배포를 못한 학생을 코딩 이해 부족으로 평가하지 않습니다.
[비상안] AI 불가: 준비된 예시를 검토하고 직접 수정. GitHub 불가: HTML과 README를 로컬로 저장하고 후속 업로드. 편집기 불가: GitHub 웹 편집으로 MY_PROFILE을 수정하되 원본을 보존. 다운로드 불가: ZIP의 templates 폴더에서 파일 제공.
[심화] P12로 색상 대비나 버튼 문구 한 가지만 바꾸고 실제 전후를 확인합니다.
